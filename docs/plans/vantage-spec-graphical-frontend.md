# 🔭 Vantage: Spec for Graphical Desktop Frontend

## Context

Following the Chocolate Doom Parity Audit and subsequent batch landings, we have restored significant source-faithfulness to the gameplay, rendering, and core audio logic. However, the `Batch D` parity pass identified a critical limitation in our current terminal-based frontend: it cannot support proper desktop mouse input, preventing true input parity with vanilla Doom. Complexity is a cost, and utility is revenue: we need to introduce a dedicated graphical desktop frontend to provide the authentic control scheme and visual presentation players expect.

This spec focuses on the "What" and the "Why" for the Graphical Desktop Frontend.

## 👤 User Story

"As a Player, I want to play the game in a dedicated graphical window with full mouse and keyboard support, so that I can aim and move exactly like I do in vanilla Doom without terminal emulator restrictions."

## 🎯 The "So What?" Ask

**What business problem does this solve?**
Without a proper graphical frontend, the engine is permanently crippled by the limitations of terminal emulators. Terminals inherently struggle with raw mouse capture (especially continuous mouselook and rapid clicking), perfectly timed keyboard event polling (key-up vs. key-down), and displaying high-framerate, tearing-free graphics. If players cannot use their mouse to turn and shoot reliably, the engine fails its parity mandate. A true graphical frontend unlocks full control parity, proper hardware-accelerated window presentation, and expands our audience beyond terminal enthusiasts.

## ✅ Acceptance Criteria

### 1. Full Input Parity
- **Success Metric:** The game must capture and process raw mouse movement and keyboard state flawlessly.
- **Criteria:**
  - Mouse movement must map perfectly to turning (and optionally forward/backward movement, matching vanilla configuration).
  - Mouse buttons must trigger actions (e.g., Left Click to fire) immediately without terminal abstraction layers.
  - Keyboard input must distinguish between key-down and key-up events to support precise movement and holding fire.

### 2. High-Performance Window Presentation
- **Success Metric:** The game must render in a dedicated, resizable window at a stable framerate without screen tearing.
- **Criteria:**
  - The software-rendered frame buffer must be efficiently blitted to the window.
  - Vsync should be supported to prevent screen tearing.
  - The window must support standard desktop interactions (resize, fullscreen, minimize).

### 3. Graceful Fallback
- **Success Metric:** The existing terminal frontend remains fully functional.
- **Criteria:**
  - The graphical frontend is a new module/crate, not a destructive replacement of `doom-tui`.
  - Players can choose which frontend to launch (e.g., via a command-line flag or by selecting a different binary).

## 🚫 Out of Scope

- **Hardware Accelerated 3D Rendering:** The graphical frontend will only display the 2D buffer generated by our existing software renderer. We are not rewriting the renderer to use OpenGL/Vulkan for 3D graphics.
- **Complex GUI Overlays:** Modern, high-resolution configuration menus layered over the game are out of scope. We will stick to the vanilla Doom menu system rendered into the game buffer.

## ⚖️ Gap Analysis

The current `doom-tui` frontend relies on `ratatui` and `crossterm`. While excellent for terminal apps, these libraries cannot provide the raw hardware input capture required for a fast-paced FPS. We lack a windowing and input management solution (like `winit` or `sdl2`) that can capture the mouse pointer, hide the cursor, and read raw delta movements. We need a new abstraction layer in `doom-app` to route input and rendering between the core game engine and this new graphical display backend.
