**Dehacked \r\n parsing panic**
**Learning:** We assumed that `Text` blocks in DeHackEd payloads would always use UNIX line endings (`\n`) following the byte bounds. However, DOS/Windows `\r\n` caused an offset bug that would strip the `\r` but leave the `\n`, thereby throwing off subsequent text parsing logic. Also, using string splitting around headers required careful `end_of_line` checking without blindly truncating strings.
**Action:** Always safely trim variable line-endings (`\r\n` and `\n`) sequentially when shifting pointers over byte slices representing text lines, especially in protocol parsers. Furthermore, when mutating byte chunks across multiple boundaries, accurately calculate lengths and test using a Chaos engineering mentality (e.g. `proptest`).
